# Every provider and agent is an ERC-8004 agent

**The sentence:** Bursar providers carry an on-chain ERC-8004 identity on Robinhood Chain, listed on 8004scan and
OpenSea, and every published ruling can update their reputation in the standard's registry.

Branch `bullish/erc8004`. Live chain 4663, settlement USDG, gas ETH. Spend on this build: about 0.00004 ETH across
three transactions, no USDG.

## What is live and what is prepared

Live on the branch, verified end to end against mainnet:

- **Agent cards** at `/agents/<address>/card.json`, the registration file ERC-8004 prescribes, built from the chain
  on each read and held for a minute. A listed provider's card carries its handle, stake, score, settlement record,
  the largest job a payer can open, its desk and the x402 facilitator. A mandate's card carries the owner, the seated
  agent, the budget and the capabilities it may spend on. An address that is neither answers 404. Served to any
  origin, so 8004scan, OpenSea and other agents read it.
- **Registration from the console.** On the provider desk, a listed provider registers its identity in one
  transaction from its own wallet: `register(agentURI, metadata)` on the standard's registry, with the card as the
  URI and a `bursar.subject` entry naming the address. On a mandate's overview, the owner registers the seated
  agent's identity the same way; the token lands in the owner's wallet and names the mandate. After the receipt the
  desk shows the id with links to 8004scan and OpenSea, and reads the token back from the registry on every refresh.
- **The identity on the desk and the mandate page**, read from the registry and never from local state: the owner's
  tokens are found through two indexes (8004scan's API, the Blockscout index), then each candidate is proved by
  `ownerOf`, `tokenURI` and `getMetadata(id, "bursar.subject")` on the registry itself. An identity that does not
  point at the live card gets a one-press "Point it at the live card" control for the wallet that holds it. The
  rulings posted against the agent by the resolver keys on record are read from the reputation registry.
- **The demo page** at `/demo/erc8004`, showing the registered demo provider live and the two-step try-it.
- **Two identities on mainnet**: agent #8754 for the demo provider and agent #8756 for the example mandate's agent.

Prepared, switched on by the operator:

- **Rulings as reputation.** The resolver service posts each finalised ruling it journaled as feedback on the
  provider's agent: `giveFeedback(agentId, medianScore, 0, "ruling", "<record>:<disputeId>", desk URL, ruling URL)`
  from its first key. The agent id comes from the provider's card and is believed only when the identity registry
  ties the token to the payee. The journal and the registry are both checked before a post, so nothing is posted
  twice. Off until `RESOLVER_REPUTATION=on` is set on the service, because every entry in that registry is public and
  permanent.

| ReputationRegistry | `0x8004BAa17C55a88189AE136b182e5fdA19dE9b63` | Proxy, implementation `0x16e0fa7f7c56b9a767e34b192b51f921be31da34`; same as Base, code hash identical (`0x38602de9…fd00b`). `getIdentityRegistry()` answers the identity registry above. `getVersion()` 2.0.0. |

Both are the standard's own deployments, listed for Robinhood Chain in the reference repository
(`erc-8004/erc-8004-contracts`, README, "Robinhood Chain Mainnet"). The spec was read from
`ethereum/ERCs/ERCS/erc-8004.md`.

Registration, from the implementation (`IdentityRegistryUpgradeable.sol`):

```solidity
struct MetadataEntry { string metadataKey; bytes metadataValue; }
function register(string agentURI, MetadataEntry[] metadata) external returns (uint256 agentId);
function register(string agentURI) external returns (uint256 agentId);
function setAgentURI(uint256 agentId, string newURI) external;
function getMetadata(uint256 agentId, string key) external view returns (bytes);
event Registered(uint256 indexed agentId, string agentURI, address indexed owner);
```

The token is minted to `msg.sender`. The key `agentWallet` is reserved: it starts as the owner and changes only with
the new wallet's signature. The card the URI resolves to must carry `type`
(`https://eips.ethereum.org/EIPS/eip-8004#registration-v1`), `name`, `description`, `image`, `services[]` (name,
endpoint, optional version), `x402Support`, `active` and `registrations[]` (`agentId`, `agentRegistry` as
`eip155:4663:<registry>`); `supportedTrust` is optional. Bursar's cards carry all of these and a `bursar` block with
the figures the description is written from.

Feedback (`ReputationRegistryUpgradeable.sol`): `giveFeedback(agentId, int128 value, uint8 valueDecimals, tag1,
tag2, endpoint, feedbackURI, bytes32 feedbackHash)`; the sender must not be the agent's owner or operator, which is
why a provider cannot rate itself and a resolver key can. `getSummary(agentId, clients[], tag1, tag2)` sums it on
chain for a chosen set of clients; the console reads it for the resolver keys on record.

## What the operator must do

1. **Deploy the console** from this branch (the card route, the discovery route, the identity sections and the demo
   page ship with it). On the web service set `NEXT_PUBLIC_SITE_URL=https://app.bursar.world` if it is not already
   set, so cards and new registrations name the live host; `BLOCKSCOUT_API_KEY` is already there and is what the
   discovery route uses beside 8004scan's API. Then read
   `https://app.bursar.world/agents/0x5210D8df060A9D5ce4c1305045ED5c9548fca374/card.json` and expect the JSON above
   with `registrations: [{ "agentId": 8754, … }]`.
2. **Point #8754 at the live card**: open the demo provider's desk with the payee wallet and press "Point it at the
   live card", or send `setAgentURI(8754, "<card URL>")` from the payee key. #8756 already points at its live card.
3. **Switch rulings on** when ready: on the resolver service set `RESOLVER_REPUTATION=on` and, if the console host
   differs, `RESOLVER_CARD_BASE`. The first resolver key pays about 100k gas per post. Nothing else changes; a
   journaled, finalised dispute whose provider has an identity is posted once, under the tag `ruling`, and shows on
   the desk as "Rulings posted" and on 8004scan under Feedback.
4. No governance action, no new contract, no new service. The registries are the standard's and already live.
5. Push the branch and open the pull request against `main`.

## Honest limits

- A fresh registration shows on the desk from the receipt at once; the indexes that list identities by owner pick
  it up within minutes, and until then the card's `registrations` list is empty for a card built on another
  machine. OpenSea and 8004scan refresh metadata on their own schedule; both showed #8754 within the hour.
- The console can show "whether this address has an identity is unknown" when both indexes are unreachable. It
  never guesses.
- A mandate's identity belongs to the mandate owner, because the registry mints to the sender. The seated agent is
  named in the card and the mandate in `bursar.subject`; `agentWallet` stays the owner's address, since changing it
  needs the agent's own signature.
- Rulings reach the reputation registry only once the operator switches the resolver to post them, and only for
  disputes the service journaled. No ruling has been posted yet. The feedback value is the median score, 0 to 100;
  8004scan's "overall score" is its own aggregation over all feedback, which Bursar does not control.
- There is no validation registry on this chain, so nothing is posted there.
- Discovery depends on two third-party indexes; the registry itself has no list per owner and its full history is
  too long to scan from a browser. Every id shown has been read back from the registry regardless.

## Announcement

**One line.** Every Bursar provider now carries an ERC-8004 identity on Robinhood Chain, registered from its desk in
one transaction and listed on 8004scan and OpenSea.

**One paragraph.** A provider on Bursar can now register an ERC-8004 identity from its desk. One transaction mints
the token in the standard's registry on Robinhood Chain and points it at a card Bursar serves from the chain: the
handle, the stake, the settlement record, the largest job a payer can open and where to reach it. 8004scan and
OpenSea list it alongside every other agent on the chain. A mandate owner can give the agent on a mandate the same
identity. Rulings on contested jobs can be posted as feedback in the ERC-8004 reputation registry, so a stranger
reads a provider's record in the same place as every other agent's.

**One post.** Bursar providers are ERC-8004 agents.

ERC-8004 gives an agent a portable identity: a token in a registry that lives at the same address on every chain it
reaches, pointing at a card that says what the agent is and where to find it. The registry on Robinhood Chain already
holds thousands of agents.

From today a provider registers its identity from its Bursar desk in one transaction, paid in ETH for gas and
nothing else. The card is served by Bursar from the chain, so the handle, the stake, the score, the record and the
largest job a payer can open are read from the contracts, never typed in. 8004scan and OpenSea pick the identity up
within minutes.

A mandate owner can register the agent seated on a mandate the same way. Its card names the owner, the agent, the
budget and the capabilities it may spend on.

Rulings on contested jobs can be posted as feedback in the ERC-8004 reputation registry, under the tag `ruling`,
from Bursar's resolver keys. A provider's record then reads where every other agent's does.

Try it on the demo provider: app.bursar.world/demo/erc8004.
